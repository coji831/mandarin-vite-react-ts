**Last Updated:** September 4, 2026
**Purpose:** Durable owner operations guide covering production **and** preview secrets/key rotation: what the owner pastes into GitHub, what to rotate at T+0, and which fixed identifiers to keep. **Cutover event note:** this rotation is tied to per-PR preview isolation (cutover 2026-08/09); it was last applied for the `epic-24-…` release (PR #54).

> **No real secret value appears in this document.** Every runtime value is marked `{GENERATE_AT_RUNTIME}` and must be generated at rotation time and entered directly into the owning console (Railway, GitHub, GCP, Neon, Upstash, Vercel) — never committed, never pasted into a doc or chat.
>
> **Scope rule (prod vs preview):** the preview environment's per-PR secrets are **auto-generated by `.github/workflows/preview.yml`** and are independent of prod (see §3). This guide is mostly about **prod** secrets plus the **GitHub-level** inputs that `preview.yml` needs to exist before any PR provision can succeed.

## 1. Purpose & Scope

The backend reads its environment from **`apps/backend/src/shared/config/index.ts`** — the authoritative env list. `validateConfig()` throws at boot if any of the **7 fail-fast criticals** is missing: `DATABASE_URL`, `JWT_SECRET`, `JWT_REFRESH_SECRET`, `GCS_BUCKET_NAME`, `GCS_CREDENTIALS_RAW`, `GOOGLE_TTS_CREDENTIALS_RAW`, `GEMINI_API_CREDENTIALS_RAW` (the last three validated via `client_email`).

Four surfaces are in scope:

| Surface                                           | Where                                                      | Rotation owner                        |
| ------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------- |
| **Railway prod environment** (the NestJS service) | Railway Dashboard → prod service → Variables               | Owner (T+0)                           |
| **Railway preview environments** (`pr-<n>`)       | Railway Dashboard → per-PR env → Variables                 | Auto (`preview.yml`)                  |
| **GitHub Actions secrets/vars** (repo level)      | GitHub → repo → Settings → Secrets and variables → Actions | Owner (pre-merge)                     |
| **Vercel project env vars**                       | `terraform/vercel.tf` (Terraform-managed)                  | Not a secret — `terraform apply` only |

The **reason** this rotation exists: env isolation was hardened at the 2026-08/09 NestJS cutover (R1 per-env JWT + `JwtService` env claim; R2 probe gate + per-env GCP → preview SA). Before per-env isolation, prod and preview shared the same JWT secrets and preview inherited prod GCP admin credentials, so prod secrets are **assumed exposed** until rotated. See [`env-isolation.md`](./env-isolation.md) for the full R1–R6 risk table.

## 6. Rotation Ordering & Sequencing (No-Downtime)

**Key structural fact:** `JwtService` verifies with **only the current env secret** — there is **no dual-secret (old+new) acceptance window**. New values take effect only when Railway restarts the service (env is read at boot). Plan each cutover as _update var → deploy/restart → verify → retire old_.

### Global order

1. **Pre-merge (owner, on branch):** `terraform apply` (additive `preview-service` SA + sandbox bucket — see [`terraform-state-recovery.md`](./terraform-state-recovery.md)) → store `GCP_PREVIEW_SA_KEY` (§2) → create/seed the Neon `demo` parent branch (preview `parent_branch: demo`).
2. **Merge → Railway prod deploy** (NestJS) → **post-flip smoke**: `node apps/backend/scripts/pr-smoke.mjs https://mandarin-vite-react-ts-production.up.railway.app` + T+0→24h watch.
3. **T+0 JWT rotation** (below).
4. **T+0 GCP prod SA rotation** (below).
5. Everything else is on-leak/periodic and independent.

### JWT — Option A (rotate both now) vs Option B (staged, zero-logout)

Access tokens are 15 min (JSON body, `Authorization: Bearer`); refresh tokens are 7 days (`httpOnly` `refreshToken` cookie, server-side session row, rotated per refresh).

- **Option A — rotate both now (recommended for this cutover):** change `JWT_SECRET` **and** `JWT_REFRESH_SECRET` → deploy. Old refresh tokens stop verifying → every logged-in user re-logs in once. Negligible for a small owner + demo-user base; matches the env-isolation R1 plan ("prod rotation at T+0 — one re-login accepted").
- **Option B — zero-logout staged:** (1) rotate **`JWT_SECRET` only** → deploy — old access tokens die in ≤15 min but the auto-refresh flow still works (refresh tokens are signed by the unchanged `JWT_REFRESH_SECRET`, and the DB session is valid); **no user is logged out**. (2) **Wait ≥ 7 days** (the refresh-token max lifetime) → rotate `JWT_REFRESH_SECRET` → deploy — only users inactive >7 days would re-login.

> Out-of-order failure: rotating `JWT_REFRESH_SECRET` before the 7-day drain forces logouts; rotating `JWT_SECRET` alone is always safe. Orphaned session-table rows remain after either option but are harmless (their tokens no longer verify).

### GCP prod SA rotation — create → update → redeploy+verify → delete

1. GCP IAM console → each of `tts-service` / `gemini-service` / `gcs-storage-service` → **Create Key (JSON)** (§4 commands).
2. One-line each (`jq -c`) → replace `GOOGLE_TTS_CREDENTIALS_RAW` / `GEMINI_API_CREDENTIALS_RAW` / `GCS_CREDENTIALS_RAW` in Railway prod Variables.
3. **Deploy/restart** (env read at boot) → verify: health endpoint reports `gemini: true, tts: true`; run `pr-smoke.mjs`; exercise one TTS + one GCS read.
4. GCP IAM console → **delete the old key** (or keep one extra generation for a safety window, then delete).

> Out-of-order failure: deleting the old GCP key before the Railway var is updated/redeployed = prod 5xx on TTS/Gemini/GCS. No code re-deploy is required — only the Railway variable change + restart.

### Preview independence (verified)

Per-PR JWTs are **fully independent of prod**: `preview.yml` mints fresh `openssl rand -hex 48` secrets per PR, sets `APP_ENV=pr-<n>`, and `JwtService` rejects tokens whose `env` claim ≠ the current `APP_ENV` (defense-in-depth even if secrets matched). A token from a PR env can never verify in prod or another PR env, and prod tokens never verify in a PR env. Preview GCP creds use the sandbox `preview-service` SA + `pinyin-pal-preview-data` bucket only — they cannot touch prod GCS. **No prod action is needed to make preview secure** — only to keep prod's own secrets fresh.

> Rotating `GCP_PREVIEW_SA_KEY` only affects _new/next_ PR provisions; open PRs keep using the key value they were given (rotate carefully if open PRs matter).

## 7. Owner Checklist

### Before merge (release pre-requisites)

- [ ] **Terraform (local, on branch):** `cd terraform && terraform apply` (additive `preview-service` + `pinyin-pal-preview-data`) — never rely on `terraform-apply.yml` (empty state; see [`terraform-state-recovery.md`](./terraform-state-recovery.md)).
- [ ] **GCP IAM console → `preview-service` → Create Key** → paste the single-line JSON into GitHub → Actions → `GCP_PREVIEW_SA_KEY`.
- [ ] **GitHub → Actions → Variables:** confirm/set `NEON_PROJECT_ID=withered-king-06089521`, `RAILWAY_PROJECT_ID=83025af1-4232-4ce1-97b9-ae25bf2d8ae2`, `RAILWAY_BACKEND_SERVICE_ID` (`{OWNER: fetch}`), optionally `GCS_PREVIEW_BUCKET_NAME=pinyin-pal-preview-data`.
- [ ] **GitHub → Actions → Secrets:** confirm `NEON_API_TOKEN`, `RAILWAY_API_TOKEN` present (preview.yml); `GCP_TF_SA_KEY`, `UPSTASH_API_KEY`, `UPSTASH_EMAIL`, `VERCEL_API_TOKEN` present (terraform workflows).
- [ ] **Neon console:** create + seed the `demo` branch (preview parent, R3).
- [ ] **Railway:** PR deployments enabled; no conflicting Preview-environment overrides; add `smoke` as a **required status check** in GitHub branch protection.

### T+0 (right after the prod deploy passes post-flip smoke)

- [ ] **Railway → prod backend service → Variables:** rotate `JWT_SECRET` and `JWT_REFRESH_SECRET` (two × `openssl rand -hex 48`, must differ) → Deploy → verify login/refresh.
- [ ] **Railway → prod Variables:** confirm `APP_ENV` is **absent** (or exactly `production`) and `HEALTH_PROBE_EXTERNAL` is **absent**.
- [ ] **GCP IAM → prod SAs → new keys** → update the 3 Railway vars → Deploy → run health (`gemini: true, tts: true`) + smoke → **delete old keys**.
- [ ] **Railway → prod Variables:** confirm `FRONTEND_URL=https://mandarin-vite-react-ts.vercel.app` (CORS allowlist).
- [ ] **Vercel:** no change needed (`VITE_API_URL` is Terraform-managed). Optional cleanup: remove any vestigial Railway-side `VITE_API_URL` reference var if the Railway → Vercel integration is not actually connected.
- [ ] **Post-flip smoke:** `node apps/backend/scripts/pr-smoke.mjs https://mandarin-vite-react-ts-production.up.railway.app`.

### Later / on-leak (no urgency)

- [ ] **Neon:** rotate `NEON_API_TOKEN` (scoped); reset the prod DB password → update Railway `DATABASE_URL`.
- [ ] **Upstash:** reset the Redis password → update Railway `REDIS_URL`.
- [ ] **Consoles:** rotate `VERCEL_API_TOKEN`, `RAILWAY_API_TOKEN`, `UPSTASH_API_KEY` as needed.
- [ ] **GCP:** rotate `GCP_TF_SA_KEY` (TF CI SA — first identify its email via `gcloud iam service-accounts list`); rotate `GCP_PREVIEW_SA_KEY` on the same cadence.
- [ ] **Chromatic:** add `CHROMATIC_PROJECT_TOKEN` only if activating visual regression.
