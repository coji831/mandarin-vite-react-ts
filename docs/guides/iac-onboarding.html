2 · Three environments — and why there is no “Develop”

Production auto main merge → Vercel prod + Railway prod + terraform-apply.yml. Owner post-flip smoke + T+0→24h watch + prod JWT rotation at T+0.
vs
Preview auto provision + smoke + teardown per-PR: Neon branch + Railway pr-<n> env + per-env secrets, gated by preview.yml smoke. Torn down on PR close.
vs
Develop skipped no persistent staging surface. If ever needed, open a long-lived PR and reuse its preview env.
Why no Develop: the per-PR preview environment is the smoke/staging surface. Merging to main is a two-fold gate — machine (required status checks quality · smoke · storybook all green) and human (per-env R1/R2 upserts verified). A third environment would duplicate that surface for no benefit.

3 · What happens during each deploy

3.1 PR open / sync → preview.yml

1 · Neon clone demo branch → preview/<head> branch (parent_branch: demo). Verify _prisma_migrations is populated (schema copy from prod/demo).
→
2 · Railway pr-<n> env waits for the PR environment, then upserts per-PR vars: DATABASE_URL (Neon preview) · JWT_SECRET/JWT_REFRESH_SECRET (openssl rand -hex 48) · APP_ENV=pr-<n> · HEALTH_PROBE_EXTERNAL=false.
→
3 · GCP → preview SA all three *_CREDENTIALS_RAW ← GCP_PREVIEW_SA_KEY, and GCS_BUCKET_NAME → sandbox pinyin-pal-preview-data (or the GCS_PREVIEW_BUCKET_NAME var — optional, same default).
→
4 · smoke job (merge gate) resolves the exact pr-<n> URL and runs apps/backend/scripts/pr-smoke.mjs. Fails closed — required status check.
PR close → cleanup cleanup job (Neon-only) deletes the Neon preview/<head> branch, and the Railway pr-<n> env is deprovisioned. Vercel auto-removes the branch preview deployments on merge/close (Vercel-native; no env-var row to prune — the per-PR Vercel automation was removed 2026-09-04).

3.2 Merge to main → production

1 · Vercel prod deploy git integration auto-deploys the SPA on push to main.
→
2 · Railway prod deploy railway.toml: build → db:migrate:deploy (preDeploy) → start (node dist/nest/main.js) → healthcheck. A failed migration blocks deploy.
→
3 · terraform-apply.yml only when terraform/** changed. State is remote in gs://pinyin-pal-tfstate (2026-09-03) — CI terraform init reads the shared GCS backend; the CI SA needs bucket access (owner grant, see terraform/README.md).
→
4 · Owner verification post-flip prod smoke — apps/backend/scripts/pr-smoke.mjs against the Railway prod URL — then T+0→24h watch. Prod JWT rotation at T+0 (openssl rand -hex 48).

4 · 🔑 Key / secret rotation

The cardinal rule of rotation: create → update the target → redeploy + verify → delete the old value. GCP allows max 10 keys per service account, so retire old keys promptly. Rotate the prod secrets at T+0 after any cutover that introduces per-env isolation (see secret-rotation.md).

4.1 The 7 fail-fast criticals (Railway prod)

validateConfig() in apps/backend/src/shared/config/index.ts throws at boot if any of these is missing — the app will not start. All live in Railway prod → Variables:

  • DATABASE_URL (Neon prod)
  • JWT_SECRET · JWT_REFRESH_SECRET
  • GCS_BUCKET_NAME · GCS_CREDENTIALS_RAW (SA: gcs-storage-service)
  • GOOGLE_TTS_CREDENTIALS_RAW (SA: tts-service) · GEMINI_API_CREDENTIALS_RAW (SA: gemini-service)
APP_ENV must stay unset (or exactly production) on prod. The JwtService env claim defaults to production when unset; any other value would break all prod token verification.
