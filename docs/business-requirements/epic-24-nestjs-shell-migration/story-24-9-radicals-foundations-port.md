# Story 24.9: Radicals + Foundations Port

## Description

**As a** backend engineer,
**I want to** port the `radicals` module — **4 routes**: `GET /v1/radicals`, `GET /v1/radicals/:radicalId`, `GET /v1/radicals/character/:glyph`, `GET /v1/radicals/:radicalId/characters` — and the `foundations` module — **4 routes**: `GET /v1/foundations/data/pinyin-tones`, `GET /v1/foundations/data/pinyin-character-map`, `GET /v1/foundations/data/strokes` **+ `GET /v1/characters/:glyph`** (the character-detail route served by the **`FoundationsController`**, i.e. the cross-module `/:glyph` route that shadows the characters module's single-segment `:glyph` on the live app) — from Express (`RadicalsController.ts`/`radicalsRoutes.ts` + `FoundationsController.ts`/`foundationsRoutes.ts`) to the NestJS 11 shell under `modules/<name>/nest/`,
**So that** the radicals + foundations surfaces become contract-identical on the Nest shell — **the cheapest ports** (both zero-dep public reference-data modules) — and the **cross-module `/:glyph` route-shadowing deferred from 24-8 is resolved** (foundations' `characters/:glyph` captures every single-segment `GET /v1/characters/<x>`, matching the Express mount order), proven by a dedicated DB-gated parity harness (real Express vs real Nest) that keeps the migration additive with the Express production path untouched until the 24-15 cutover.

## Business Value

The radicals + foundations port is the mid-migration batch's **zero-dependency pair** — the cheapest possible ports, de-risking the serial ramp into the dependency-carrying batch (24-10 audio, 24-11 review, 24-12 readers, 24-13 quiz/progression). Both modules are public static reference data (radicals = the radical reference table + the `CharacterRadical` junction; foundations = pinyin/tones/strokes reference pools + character detail), so each port is a mechanical 1:1 of its Express container factory with no auth, no cache, no external clients. The real de-risker is the **route-shadowing resolution deferred from 24-8**: on the live Express app, the foundations router is mounted before the characters router (`src/app/routes.ts`), so foundations' `GET /v1/characters/:glyph` **owns** the single-segment character path — every `GET /v1/characters/<x>` (including `/search` and `/frequency`) returns the foundations shape/404, not the characters module's handlers. 24-8 ported characters first and documented this as a deferred parity item; 24-9 closes it by reproducing the **module-import order** on the Nest shell (foundations before characters), so the shell's route table matches Express byte-for-byte — including the two shadowed characters paths. A dedicated DB-gated parity harness (`radicals-foundations-parity.test.ts`, 14 tests) proves 2xx deep-equal body parity (deterministic full-table reads) and 4xx envelope parity (`code`/`message` byte-for-byte equal to the Express legacy bodies), plus the two parity edge cases the harness must pin: the `GET /v1/radicals/:radicalId` **`200 null`** wire body (unknown ID) and the cross-module shadow itself. This de-risks the remaining ports by proving both a **route-order-sensitive module pair** and the **cross-module shadow mechanism** (module import order = route registration order) that the shell must preserve.

## Business Rules

1. **Routes are verbatim from `ROUTE_PATTERNS`** — `radicals`/`radicalsById`/`radicalsByCharacter`/`radicalsCharacters`/`foundationsPinyinTones`/`foundationsPinyinCharacterMap`/`foundationsStrokes`/`charactersByGlyph` (`/v1/radicals/*`, `/v1/foundations/data/*`, `/v1/characters/:glyph`, `/api` prefix applied by the shell); the Nest controllers mirror the Express controllers 1:1, reusing the framework-agnostic services unchanged.
2. **Envelope parity (24-3 contract)** — radicals Express bodies carry `{error, code}` → the Nest envelope's `code` equals the Express `code` and `message` equals the Express `error`; foundations Express bodies carry a plain `{error}` (no `code`) → the Nest envelope supplies a `code` per the backend error-message convention (`VALIDATION_ERROR` / 400, `NOT_FOUND` / 404, `LOAD_ERROR` / 500) while `message` is byte-for-byte equal to the Express `error` text.
3. **Zero-dep reference modules** — no auth, no cache, no external clients; the radicals repos (`RadicalsRepository`/`RadicalCharacterService`) and `FoundationsService` self-import the shared Prisma singleton (matching the `words` port in 24-2 and the `characters` port in 24-8), so neither `radicals.module.ts` nor `foundations.module.ts` imports `SharedModule`.
4. **Route-order parity is preserved** — `RadicalsNestController` declares its four handlers in the same order as `radicalsRoutes.ts` (`/`, `/:radicalId`, `/character/:glyph`, `/:radicalId/characters`); e.g. `GET /v1/radicals/character` is captured by `/:radicalId` → 404 on both apps (a pre-existing latent, reproduced byte-for-byte).
5. **`200 null` wire-body parity** — `GET /v1/radicals/:radicalId` for an UNKNOWN ID returns **200 with a literal `null` body** on Express (`res.json(null)`); the Nest handler mirrors it with a full `@Res()` `res.json()` (Nest's default reply would strip the null → empty body). The reachable 404 (`GET /v1/radicals/:radicalId/characters` unknown → `NOT_FOUND`) still flows through the global `AppExceptionFilter`.
6. **Cross-module route-shadowing is reproduced via module-import order** — `FoundationsModule` is imported BEFORE `CharactersModule` in `app.module.ts` (Nest registers routes in module-import order onto the same Express router; first-match-wins, no conflict detector fires), matching the Express `src/app/routes.ts` mount order (foundations L60, characters L126); `GET /v1/characters/search` + `/frequency` remain shadowed on BOTH apps (foundations 404) — a pre-existing latent, parity preserved, no new bug.
7. **Additive-only** — the Express radicals/foundations wiring is untouched; the Nest surface coexists until the module cutover (24-15). No `packages/shared-constants` / `packages/shared-types` / FE change.
